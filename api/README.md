# Сервис приёма событий

Принимает события от плагина ExpeditionCore, складывает их в журнал и раз в минуту
пересобирает снимки, которые читает сайт. Форматы — в [`../docs/contract/api-v1.md`](../docs/contract/api-v1.md).

## Запуск

```bash
EXPEDITION_KEY=secret-key npm run api
```

Запускается через `tsx`, а не голым `node`. Собственное разбирательство TypeScript у Node
появляется только в официальных сборках 22.18 и новее — на Node из репозитория Ubuntu
его нет вовсе, и `node api/src/main.ts` падает с «Node.js is not compiled with TypeScript
support». Зависеть от того, чьей сборкой запущен сервис, не хочется.

| Переменная | По умолчанию | Зачем |
| --- | --- | --- |
| `EXPEDITION_KEY` | — | Секрет, которым подписывается каждый запрос плагина. Обязателен |
| `PORT` | `4000` | Порт приёма |
| `EVENT_LOG` | `data/events.jsonl` | Журнал событий |
| `DATA_DIR` | `public/data` | Куда писать снимки для сайта |
| `SEASON_STARTS_AT`, `SEASON_STORY_ENDS_AT` | — | Даты сезона: событиями они не приходят |

Во время сезона приёмник поднимается в докере вместе с игрой — `server/docker-compose.yml`,
образ из `Dockerfile` рядом. Двух сразу запускать нельзя: они пишут один журнал и одни
снимки, и порт `4000` всё равно занят. Для разработки останови сезонный: `docker compose stop api`.

**Ключ обязан быть из латиницы и цифр.** Заголовки HTTP не переносят не-ASCII, кириллический
ключ доедет искажённым, и приём будет молча отвечать «неверный ключ». Проверено на живом
сервисе, поэтому сервис теперь падает на старте, а не молчит.

## Как устроено

**Журнал вместо базы.** События дописываются в `events.jsonl` по одному на строку. Журнал
переживает перезапуск, читается глазами и позволяет пересобрать снимки заново в любой момент.

Здесь стояло «пара мегабайт», и это была ошибка счёта: строк действительно десятки тысяч,
но сигнал раз в минуту несёт полный список тех, кто в сети. Замер на сезоне в 90 дней
и 20 игроках — **315 МБ файла и 648 тысяч строк**.

**В памяти живёт не журнал, а рабочий набор** — те события, которые ещё могут изменить
снимки. Сигналы и слепки статистики только перезаписывают поля игрока, поэтому из них
хранятся последний сигнал, последний слепок каждого и по первому с последним событию
на игрока: остальные заведомо перезаписаны. Тот же замер после этого — **104 МБ кучи
вместо 1,5 ГБ и 22 события вместо 648 тысяч**. Файл при этом остаётся полным: он и есть
история сезона.

**Снимки пересобираются целиком**, а не правятся по месту: `applyEvents` сводит рабочий
набор за раз. Это миллисекунда (до рабочего набора было 400 мс на каждую минуту), зато
нет ни одного состояния, которое можно испортить частичным обновлением.

Что остаётся расти — множество номеров принятых событий: оно и держит обещание «повтор
молча пропускается». На 648 тысячах это около ста мегабайт. Повтор, который всё же
проскочит, снимков не испортит — сборка отсеивает повторы по тому же номеру.

**Запись атомарная** — во временный файл и переименование. Иначе сайт может прочитать
половину файла, если запрос застал запись на середине.

## Проверка

```bash
curl http://localhost:4000/health
curl -X POST http://localhost:4000/events -H 'X-Expedition-Key: secret-key' \
  -d '{"id":"e1","v":1,"type":"server.heartbeat","at":"2026-10-20T21:00:00Z","online":[]}'
```

Повторная отправка того же события отвечает успехом с пустым `accepted` — плагин имеет
право слать одно и то же сколько угодно раз.
