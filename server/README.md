# Сервер сезона

Игра и приёмник событий поднимаются одной командой и живут в общей сети докера:
плагин шлёт события по имени `api`, и наружу этот обмен не выходит.

```bash
cp .env.example .env   # и подставить свой ключ
docker compose up -d
docker compose logs -f minecraft
```

Остановить — `docker compose down`. Мир при этом цел: он лежит в `data/` на диске,
а не внутри контейнера.

## Что где лежит

| Каталог | Что в нём | В репозитории |
| --- | --- | --- |
| `data/` | Мир, конфиги Paper, логи, настройка плагина | нет |
| `plugins/` | `jar`-файлы: чужие и собранный ExpeditionCore | нет |
| `../public/data/` | Снимки для сайта: `api` пишет, сайт читает | нет |
| `../data/` | Журнал событий сезона `events.jsonl` | нет |

Под версией здесь только `docker-compose.yml`, этот README и `.env.example`. Мир —
не исходник, чужие `jar` не наши, а ключ секрет. Восстанавливается всё, кроме мира:
образы тянутся сами, ExpeditionCore собирается из `../plugin/`.

## Обновить плагин

```bash
cd ../plugin/ExpeditionCore && ./gradlew build
cp build/libs/ExpeditionCore-0.1.0.jar ../../server/plugins/
cd ../../server && docker compose restart minecraft
```

Перезапуск обязателен: настройку плагин читает один раз при включении, а `jar`
образ переносит из `plugins/` в `data/plugins/` на старте.

## Ключ

`EXPEDITION_KEY` в `.env` — одно значение на обе стороны. Плагин берёт его из
окружения, а не из `config.yml`: секрету не место в файле, который уезжает
в репозиторий и в архив с бэкапом.

Ключ обязан быть из латиницы и цифр. Заголовки HTTP не переносят кириллицу —
такой ключ доедет искажённым, и приём будет молча отвечать «неверный ключ».
Обе стороны падают на старте, если ключ негоден, вместо того чтобы выяснять
это на первой находке сезона.

## Обнулить сезон

Перед стартом репетиционные данные надо убрать, иначе сезон начнётся с чужими
находками, открытыми разделами и чужим первооткрывателем во всех строках.

Состояние лежит в трёх местах, и третье не очевидно.

```bash
docker compose down                        # плагин пишет state.txt на остановке

rm -f ../data/events.jsonl                 # 1. журнал сезона
rm -f ../public/data/*.json                # 1. снимки для сайта

rm -f data/plugins/ExpeditionCore/state.txt      # 2. что плагин уже отправил
rm -f data/plugins/ExpeditionCore/outbox.jsonl   # 2. очередь
rm -f data/plugins/ExpeditionCore/rejected.jsonl # 2. отвергнутое

rm -f data/world/stats/*.json              # 3. ванильная статистика
rm -f data/world/playerdata/*.dat*         # 3. счётчик поставленных блоков

docker compose up -d
```

**Третий пункт забыть легче всего.** Добытое, убитые и время игры считает не плагин,
а сама ваниль, и живут эти счётчики в мире, а не в журнале: `world/stats/<uuid>.json`.
Пустой журнал их не трогает — сезон стартует с одиннадцатью часами наигранного времени
у того, кто отлаживал. Счётчик поставленных блоков плагин держит в `PersistentDataContainer`
игрока, то есть в `world/playerdata/<uuid>.dat`, и он переживает то же самое.

Мир при этом остаётся: снос статистики не трогает ни построек, ни ландшафта. Если
сезон играется на новом мире, третий пункт не нужен — он уезжает вместе со старым.

Порядок важен: сначала остановка. Плагин роняет `state.txt` на диск при выключении,
и удалённый на живом сервере файл вернётся через минуту.

## Если события не доходят

Очередь плагина лежит на диске и переживает и падение `api`, и падение сервера,
поэтому спешить некуда — ничего не потеряется.

```bash
docker compose exec minecraft rcon-cli expedition status   # длина очереди и последняя ошибка
curl -s localhost:4000/health                              # жив ли приёмник
docker compose logs api
```
