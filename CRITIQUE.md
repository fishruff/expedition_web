# Разбор проекта Expedition — без скидок

Разбор всего, что лежит в `expedition_web`: сайт, `api`, плагин, докер, конфиги сервера,
ассеты, документация. Тон намеренно жёсткий: просили не жалеть. Порядок — по тому,
насколько больно будет, когда это выстрелит.

Сразу оговорка, чтобы дальше было честно: проект сделан **сильно лучше среднего**.
Архитектура «плагин → журнал событий → снимки → статика» правильная, комментарии
объясняют «почему», а не «что», тесты есть и они осмысленные. Именно поэтому
дальше — только про то, что сломано, недоделано или врёт.

---

## 0. То, из-за чего сезон может не состояться

### 0.1. Сервер открыт всему интернету и раздаёт оператора по нику

`server/data/server.properties`:

```
online-mode=false
white-list=false
enable-rcon=true
rcon.password=8b4c04d71a29b3a5e35d15f6
```

Это не «мелкая настройка», это дыра в основании всего проекта:

- **`online-mode=false` + `white-list=false`** = зайти может кто угодно, под любым ником.
  В `server/data/ops.json` лежит `fish_ruff` с `level: 4`. Любой человек, который узнает
  адрес, заходит с ником `fish_ruff` и получает **полного оператора**. Дальше он ставит
  метки на предметы (`/expedition record ...`), открывает разделы сайта, выдаёт себе
  находки, стирает мир. Весь «сюжет сезона» ломается за минуту.
- **UUID перестают быть UUID.** Вся система склейки построена на «ник можно сменить,
  uuid — никогда» (`src/data/merge.ts:44`, `api/src/apply.ts:18`, `:77`). В offline-режиме
  uuid **вычисляется из ника** (v3-хеш — это видно прямо в `ops.json`: `...-3d89-...`,
  `...-3788-...`, версия 3). То есть весь фундамент «ключ — uuid» держится на нике,
  просто окольным путём. Сменил ник — стал другим человеком. Совпал ник — украл статистику.
- **`ops.json` уже испорчен**: там сидит `"name": "soooobaka\\"` с обратным слешем и
  `level: 4`. Это либо опечатка, либо след того, как offline-режим уже пропустил мусор.
  У этого «игрока» права оператора.
- **RCON включён с паролем в открытом виде** и `broadcast-rcon-to-ops=true`. Порт 25575
  в `docker-compose.yml` наружу не проброшен — это спасает. Пока.

**Что делать:** `online-mode=true` (или, если принципиально offline, — `white-list=true`
плюс прокси с авторизацией), почистить `ops.json`, сменить пароль RCON.
До этого запускать сезон нельзя вообще.

### 0.2. Сервер падал шестнадцать раз, и никто это не разбирал

`server/data/hs_err_pid*.log` — **16 дампов SIGSEGV**. Причина одна и та же:

```
C  [spark-...-libasyncProfiler.so.tmp+0x270e9]  VMThread::nativeThreadId(...)+0x59
JRE version: OpenJDK Temurin-25.0.3+9
```

Два вывода, оба неприятные:

- **Падает профилировщик Spark**, при том что в `server/docker-compose.yml` стоит
  `ENABLE_SPARK: "false"`. Значит запущенная конфигурация **не соответствует** тому,
  что лежит в репозитории. Compose — фикция, реальный сервер настроен где-то ещё руками.
- **Java 25**, хотя compose говорит `JAVA_VERSION: "21"`, а `build.gradle.kts` собирает
  плагин под toolchain 21. Ещё одно расхождение между «как записано» и «как есть».

Шестнадцать сегфолтов в проекте, где отдельный раздел README посвящён тому, что
«первая находка сезона невосстановима», — это не мелочь, которую можно не заметить.
Дампы просто лежат в каталоге и никем не открыты.

## 1. Функциональные баги — видны пользователю

### 1.1. Раздел «Карта» показывает пустой прямоугольник

`src/shared/assets.ts:31` объявляет `island-map.png`. В `public/assets/` **этого файла нет**.
`Sprite` честно отработает `onError` и нарисует силуэт в штриховку.

То есть раздел, который открывается находкой, ради которого на столе лежит компас
с замком, ради которого в `places.json` расставлены три метки, — при открытии
показывает **заглушку вместо карты**. Метки при этом рисуются поверх неё
(`MapSection.tsx:33`), потому что они позиционируются в процентах от контейнера.
Игрок, который наконец открыл карту, получит серую штриховку с тремя кнопками.

Это самый обидный баг в проекте: механика замка работает идеально, а за замком пусто.

### 1.2. Автоматические звания сваливаются в одну кучу

`src/content/crew.json` — **ни у одного участника нет поля `uuid`**. Ни у одного из шести.

Следствие, `src/data/merge.ts:29`: `uuid: member.uuid || entry?.uuid || ''` → пока
снимков нет, у **всех** участников `uuid === ''`.

Дальше `src/data/titles.ts:49`:

```ts
awards[member.uuid] ??= []
awards[member.uuid].push(rule)
```

Все безуuid-ные участники пишут в **один и тот же ключ `awards['']`**. Звания
перемешиваются между людьми. Сейчас это не заметно только потому, что у всех шестерых
проставлен ручной `title`, а `titleOf` (`src/data/useCrew.ts:32`) отдаёт приоритет ручному.
Стоит владельцу добавить участника без звания — и он получит чужие награды.

`Record<string, ...>` с ключом, который в половине случаев пустая строка, — это
не структура данных, это ловушка.

### 1.3. На странице участника «Найденные записи» всегда пусты, а «Артефакты» — нет

`src/sections/Crew/Player.tsx`, две строки подряд, два разных способа опознать человека:

```ts
:41  const found = snapshots.records.found.filter((r) => r.foundBy.uuid === member.uuid)
:44  const artifacts = Object.entries(...).filter(([, u]) => u.by.toLowerCase() === member.nick.toLowerCase())
```

Записи ищутся по **uuid**, артефакты — по **нику**. При этом (см. 1.2) `member.uuid`
у авторских участников пустой, пока не пришёл снимок. Результат: артефакты показываются,
записи — нет. На одной странице, в двух соседних блоках.

Корень в `api/src/apply.ts:124`:

```ts
snapshots.unlocks.unlocked[event.artifactId] = { at: event.at, by: event.player.name }
```

`api` кладёт в `by` **имя**, хотя весь остальной код religiously держится за uuid и
в комментариях объясняет, почему ник ненадёжен. То же в `zone/ZoneWatcher.java:249`:
`events.placeRevealed(zone, player.getName())`. Собственное правило нарушено дважды
в двух разных модулях.

### 1.4. Хронометр после дедлайна показывает нули и врёт подписью

`src/sections/Chronometer/Chronometer.tsx:35` + `countdown.ts:39` (`Math.max(0, msLeft)`).
Когда сюжетная часть кончилась, табло встаёт на `00 00 00 00`, а под ним по-прежнему
написано «до конца сюжетной части». Состояния «время вышло» нет вообще.
Раздел, который целиком про время, не умеет обрабатывать самый интересный момент —
момент истечения.

### 1.5. Даты показываются в UTC русской аудитории

`src/shared/lib/dates.ts` — везде `getUTCDate()`, `getUTCHours()`.

Сервер русский, игроки в MSK (UTC+3). Находка в 01:30 по Москве покажется **вчерашним
числом**. «Последняя активность: Сегодня, 22:15» будет означать 01:15 ночи по местному.
Комментарий на `:20` обещает человекочитаемость — а получается календарь чужого часового пояса.

Отдельно `formatLastSeen` считает «вчера» вычитанием ровно 86 400 000 мс (`:30`) — при
переходе на UTC это работает, но как только кто-то сделает правильную вещь и перейдёт
на локальное время, эта строка сломается молча.

### 1.6. Расстояние округляется до километров и теряет до 500 метров

`src/shared/lib/stats.ts:22`:

```ts
return metres < 1000 ? `${metres} м` : `${Math.round(metres / 1000)} км`
```

Прошёл 1 500 м → «2 км». Прошёл 47 400 м → «47 км». Игрок, который специально ходил
за званием «Ходок», увидит число, отличающееся от реального на полкилометра, и не поймёт,
почему звание у другого. Нужен хотя бы один знак после запятой.

### 1.7. Ключи React в ленте собираются из текста

`src/data/feed.ts:57`: `id: \`event-${event.title}\``.

Два события сезона с одинаковым названием (а это «Гонка за артефактом» — вещь, которую
логично повторить) дают одинаковый ключ. React ругается в консоль и путает элементы
при пересортировке. То же с `record-${recordId}` — здесь безопаснее, но принцип тот же:
ключ должен быть идентификатором, а не заголовком.

Там же `:49`: `title: record.recordId`. Если находка есть в снимке, но её нет в
`story.json`, в ленте появится сырой технический номер вида **«храм-1»** как заголовок.
`Player.tsx:117` эту же ситуацию обрабатывает правильно (`known?.title ?? record.recordId`),
а лента — нет.

### 1.8. `Sprite` навсегда запоминает неудачу

`src/ui/Sprite/Sprite.tsx:24`: `const [failed, setFailed] = useState(false)`.

Состояние не сбрасывается при смене `def`. Если React переиспользует компонент
(а он переиспользует — например, при переходе между двумя участниками, у которых
портрет в одной и той же позиции DOM), то после одной битой картинки **все следующие**
в этой позиции покажутся заглушкой, даже когда файлы есть. Нужен либо `key={def.file}`
на месте вызова, либо сброс в `useEffect`.

### 1.9. Прогресс по сюжету считается неправильно

`src/sections/Crew/Player.tsx:53`:

```ts
const progress = story.length > 0 ? Math.round((found.length / story.length) * 100) : null
```

Заголовок над этим — «Прогресс по сюжету». Но `found` — записи, найденные **лично этим
игроком первым**. Экспедиция из четырёх человек, каждый нашёл по одной записи из четырёх —
у каждого «прогресс по сюжету 25 %», хотя сюжет пройден на 100 %. Либо это личный вклад
и заголовок врёт, либо это прогресс сюжета и формула врёт. Сейчас врёт заголовок.

## 2. Надёжность: `api` и очередь

### 2.1. `api` падает от одного кривого события

`api/src/http.ts:60`:

```ts
function noteProblem(event: ExpeditionEvent, deps: Deps): string {
  const { note, player, at } = event
  ...
  if (deps.notesToday(player.uuid, day) >= MAX_NOTES_PER_DAY)
```

`looksLikeEvent` (`:38`) намеренно проверяет только `id`, `v`, `type`, `at` — и это
задокументированное решение. Но тогда `player` может отсутствовать, и `player.uuid`
бросит `TypeError`. Бросит он его **внутри колбэка `req.on('end')`** (`main.ts:67`),
где его никто не ловит → `uncaughtException` → **процесс умирает**.

Тело запроса, которое убивает приёмник:

```json
{"id":"x","v":1,"type":"note.published","at":"2026-01-01T00:00:00Z","note":{"pages":[]}}
```

`restart: unless-stopped` поднимет контейнер обратно, но между падением и подъёмом
события теряются… нет, не теряются — очередь плагина их сохранит. Зато сайт покажет
«сервер выключен», и разбираться, почему `api` циклически перезапускается, придётся в
разгар сезона. Ни `try/catch` вокруг `handle`, ни `process.on('uncaughtException')` нет.

### 2.2. Тело запроса читается без ограничения размера

`api/src/main.ts:65-73` копит `chunks` до конца запроса. `BATCH_LIMIT` (`http.ts:109`)
проверяется **после** того, как всё тело уже в памяти, и после `JSON.parse`.
Проверка ключа — тоже после.

То есть кто угодно, кто дотянется до порта, отправляет гигабайтный POST и роняет
приёмник по памяти, **не зная ключа**. В сезонной конфигурации порт привязан к
`127.0.0.1` — это спасает. Но `npm run api` при разработке слушает `0.0.0.0:4000`,
и в README это никак не оговорено.

Нужен счётчик байтов с обрывом соединения на, скажем, 1 МБ.

### 2.3. Сравнение ключа не постоянного времени

`api/src/http.ts:96`: `request.headers['x-expedition-key'] !== deps.key`.

Классический тайминг-канал. Для локальной сети — теоретический, но `crypto.timingSafeEqual`
стоит одну строку, и вы уже написали три абзаца комментариев про то, почему ключ не должен
лежать в конфиге. Раз уж относитесь к секрету серьёзно — относитесь до конца.

### 2.4. Последний сигнал при остановке сервера никогда не уходит

`plugin/.../outbox/Outbox.java:118`, javadoc:

> «Остановка: сначала запись на диск, **потом попытка отправки не дольше трёх секунд**.»

Смотрим код:

```java
public void close() {
    running = false;      // ← поток отправки после этого больше не работает
    persistNow();
    wake();
    thread.join(CLOSE_TIMEOUT_MILLIS);
```

и цикл:

```java
private void loop() {
    while (running) {          // ← false, выходим сразу
        pumpOnce();
```

Поток просыпается от `wake()`, возвращается к `while (running)`, видит `false` и завершается.
**`pumpOnce()` после `close()` не вызывается ни разу.** Трёхсекундный `join` ждёт поток,
который уже вышел.

Последствие: `ExpeditionCore.onDisable()` (`:117`) кладёт в очередь прощальный
`heartbeat` с пустым списком — специально, с комментарием на пять строк о том, что это
честнее, чем ждать три минуты тишины. Это событие **уедет только при следующем запуске
сервера**. То есть заявленное поведение не работает вообще, а комментарий утверждает обратное.

Правильно: `close()` должен позвать `pumpOnce()` сам (или выставить флаг «последний прогон»
до сброса `running`).

### 2.5. Очередь и журнал растут без потолка

- `Outbox.pending` (`Outbox.java:48`) — `ArrayList` без ограничения. `api` лежит сутки →
  очередь в памяти сервера растёт, и **весь файл переписывается целиком при каждом
  изменении** (`persist`, `:279`). Комментарий на `:25` утверждает: «В очереди обычно ноль
  строк, а при часовом простое накопится несколько сотен». При суточном простое там будут
  десятки тысяч строк, и они будут переписываться раз в секунду.
- `EventLog.events` (`api/src/store.ts:30`) держит **весь сезон в памяти** и пересобирает
  снимки из него целиком раз в минуту (`applyEvents`). README обещает «пара мегабайт» —
  но при `statsMinutes: 5` и двадцати игроках это 5 760 событий статистики в сутки только
  на снимки, плюс heartbeat раз в минуту (1 440/сутки), плюс всё остальное. За трёхмесячный
  сезон — под миллион строк. Компакции нет, ротации нет, срезки старых heartbeat нет.
- `applyEvents` при этом квадратичен: `snapshots.records.found.find(...)` внутри цикла
  (`apply.ts:97`) и два `.filter()` по всем находкам на каждого игрока (`:165`, `:168`).

Ничего из этого не взорвётся на четырёх игроках за неделю. Всё это взорвётся, если проект
проживёт дольше одного сезона, — а он на это и рассчитан.

### 2.6. Валидация ключа расходится между плагином и api

- `api/src/main.ts:36`: `/^[\x21-\x7e]+$/` — печатные ASCII без пробела.
- `plugin/.../config/Settings.java:47`: только проверка `charAt(i) > 0x7f`.

Плагин примет ключ с пробелом или управляющим символом, `api` — нет. Обе стороны читают
одну переменную, так что практически они просто по-разному упадут. Но это два независимых
списка правил для одного значения, и они уже разъехались.

## 3. Мобильные устройства: сайт нечитаем

Это самая заметная для живого человека проблема после карты.

### 3.1. Шрифт 6 пикселей на телефоне

`src/scene/useScale.ts:15`:

```ts
Math.max(MIN, Math.min(MAX, Math.floor(width / STEP)))   // STEP = 640
```

Ширина 375 (iPhone) → `floor(375/640) = 0` → `--s = 1`.

`src/styles/global.scss:69`: `font-size: px(6)` = `6px * var(--s)` = **6 физических пикселей**.

Дальше по всему проекту:

| Где | Размер при `--s: 1` |
| --- | --- |
| `global.scss:69` — весь текст сайта | **6px** |
| `Log.module.scss:52` — тело записей | **5px** |
| `Log.module.scss:82` — дата | **4px** |
| `Player.module.scss:206` — подписи карточек статистики | **4px** |
| `Desk.module.scss` — навигация, футер, счётчик онлайна | **5px** |

Для сравнения: минимально приемлемый основной текст на телефоне — 16px. Здесь 4–6.
Это **не «мелко»**, это физически нечитаемо: 4 пикселя на кириллическую букву — это
меньше, чем нужно, чтобы отличить «и» от «н».

Ступень `--s: 2` включается только с 1280px ширины. То есть **все телефоны, все планшеты
и ноутбуки до 1280 включительно** получают самый мелкий вариант. Ноутбук 1366×768 получит
`--s = 2` — 12px основного текста, что тоже мало.

### 3.2. Ни одного `rem` во всём проекте

`px()` (`_mixins.scss:18`) считает в `1px * var(--s)`. Пользователь, увеличивший размер
шрифта в настройках браузера или системы, **не получит ничего** — сайт проигнорирует
настройку целиком. Для человека со слабым зрением сайт просто не существует.

Это прямое следствие пиксельной доктрины, и доктрина здесь важнее пользователя.
Компромисс есть: привязать `--s` не только к ширине окна, но и к `1rem`, чтобы системная
настройка поднимала ступень.

### 3.3. Мобильной навигации нет

`Desk.module.scss:59`: `.nav { display: flex; gap: px(8); }` — шесть пунктов в строку,
без `flex-wrap`, без бургера, в общем ряду с логотипом и счётчиком онлайна.
`JOURNAL.md` в конце сам это признаёт: «Бургер-меню в шапке для мобильных» — не сделано.

Плюс размеры зон нажатия: `.navLink { padding-block: px(2) }` → высота касания около
10–14 физических пикселей. Рекомендация Apple/Google/WCAG — 44px и 24px минимум.
Промахиваться будут все.

### 3.4. Скачок раскладки на первом кадре

`global.scss:20-24` задаёт `--s: 2` и `--sa: 1`. `useScale` (`:38`) выставляет реальные
значения **в `useEffect`**, то есть после первой отрисовки. На телефоне первый кадр
рисуется вдвое крупнее, чем нужно, потом схлопывается. На широком экране предметы
рисуются вдвое мельче (`--sa: 1` против фактического 2), потом прыгают.

Плюс комментарий на `:23` — «Масштаб предметов и артов: они рисуются вдвое плотнее
интерфейса» — **прямо противоречит** `useScale.ts:22-28`, где на восьми строках
объясняется, что эта посылка была проверена и опровергнута. Один из двух комментариев
лжёт читателю, и это тот, который лежит в глобальных стилях.

Лечится одной строкой инлайн-скрипта в `index.html` до отрисовки.

## 5. Ассеты и пиксельная доктрина

README формулирует правила и тут же их нарушает.

### 5.1. Арты участников — не пиксель-арт и весят 1,4 МБ

README:

> **Ассеты хранятся в родном размере** — маленькими. Большой файл не улучшает картинку,
> а ухудшает.

Факты:

| Файл | Реальный размер | Объявлено в коде | Вес |
| --- | --- | --- | --- |
| `crew/freethinkel.png` | 448×600 | 144×192 (`assets.ts:72`) | **426 КБ** |
| `crew/tereon.png` | 448×600 | 144×192 | **365 КБ** |
| `crew/soooobaka.png` | 448×600 | 144×192 | **348 КБ** |
| `crew/fish_ruff.png` | 448×600 | 144×192 | **253 КБ** |

Итого **1,4 МБ** на четыре портрета в проекте, где все остальные ассеты вместе весят 30 КБ.
Атрибуты `width`/`height` у `<img>` при этом врут в три раза. Коэффициент 448/144 = 3,11 —
дробный, ровно то, что README запрещает первым пунктом. Спасает только `.illustration`
с `image-rendering: auto` (`Sprite.module.scss:28`), то есть портреты **сглаживаются**,
а всё остальное на странице — нет. Визуально они выпадают из стиля.

`crewArt(nick, version?)` (`assets.ts:69`) принимает версию для сброса кеша — и **ни один
из двух вызовов её не передаёт** (`Players.tsx:22`, `Player.tsx:60`). Владелец, который
«меняет их почти ежедневно» (комментарий на `:66`), будет менять файл и не понимать,
почему у людей старая картинка.

### 5.2. Шрифты — 566 КБ в TTF

`public/fonts/Monocraft.ttf` (210 КБ) + `Monocraft-Bold.ttf` (356 КБ). Без `woff2`
(экономия 60–70 %), без `preload`, без `unicode-range`. Оба грузятся всегда, даже если
жирный не встретился на странице. `font-display: swap` есть — уже хорошо, но
на мобильном интернете это полсекунды пустого экрана.

### 5.3. Служебные страницы уезжают в продакшн

`public/assets-preview.html` (181 строка) и `public/compare-watch.html` (123 строки) —
внутренние страницы приёмки ассетов. Всё, что лежит в `public/`, Vite копирует в `dist/`
как есть — что и подтверждается: обе уже там. После деплоя они будут открыты по
`https://ваш-домен/assets-preview.html`. Их место в `tools/` или в `docs/`.

## 7. Инфраструктура и репозиторий

### 7.1. Деплоя не существует

Роутер — `createBrowserRouter` (`router.tsx:55`). Значит для любой статики нужен
fallback на `index.html`, иначе прямой заход на `/players/fish_ruff` или обновление
страницы (F5) вернут **404**. В репозитории нет ни `vercel.json`, ни `netlify.toml`,
ни `_redirects`, ни конфига nginx. `JOURNAL.md` в разделе «Инфраструктура» пишет об этом
сам — и оставляет невыполненным.

Отдельно: `docker-compose.yml` монтирует `../public/data:/snapshots`, то есть `api`
пишет снимки в **исходники сайта**. Это работает для `npm run dev`. Для собранного
`dist/` — не работает вообще, снимков там не будет. Схема доставки данных на
продакшн-сайт нигде не описана.

### 7.2. `.gitignore` дырявый

Не игнорируется:

- `__pycache__/` — `tools/__pycache__/*.pyc` уже болтается в `git status`, два файла
  для двух версий Python.
- `incoming/` — каталог с исходниками артов: 8 картинок плюс **три файла
  `*.jpg:Zone.Identifier`** (мусор от Windows/WSL, альтернативные потоки NTFS).
  Всё это отображается как untracked и рано или поздно попадёт в `git add .`.
- `*:Zone.Identifier` — отдельно, потому что они будут появляться при каждом
  копировании файла из Windows.

### 7.3. Тринадцать файлов изменены и не закоммичены

`git status` показывает 13 изменённых файлов (включая `src/content/crew.json`,
`src/content/story.json`, `src/shared/assets.ts`, `src/shared/config/site.ts`,
три теста и три `.module.scss`) плюс 13 untracked, включая **целый новый компонент
`src/ui/PlayerHead/`**, который уже импортируется из `Archive.tsx:6`.

То есть в коммитах репозитория лежит **неработающая версия**: `Archive.tsx` там
импортирует модуль, которого нет. Кто угодно, кто склонирует репозиторий сейчас,
получит проект, который не собирается.

### 7.4. Нет CI, нет форматтера, нет лицензии

- Ни одного workflow. `npm test`, `npm run lint`, `tsc -b`, `./gradlew build` — всё
  запускается только руками. При такой плотности инвариантов между тремя подсистемами
  (контракт, ключи разблокировок, форматы дат) отсутствие CI — самое дешёвое из
  упущенного.
- Prettier нет (`JOURNAL.md` признаёт). Это видно: `LoveCommand.java` отформатирован
  совершенно иначе, чем весь остальной Java-код.
- `LICENSE` нет. Для проекта с `OFL-Monocraft.txt` внутри и чужими jar в `plugins/` —
  странно.
- В `package.json` — `"name": "expedition_web"`, `"version": "0.0.0"`. Плагин при этом
  версионируется (`0.1.0`), а контракт — тоже (`v1`). Три схемы версионирования, из
  которых одна пустая.

### 7.5. Зависимости из будущего

`package.json` требует Vite 8, React 19.2, React Router 8, ESLint 10, TypeScript 6.0,
Vitest 4, Node 22.22+. Node в системе — ровно `v22.22.1`, ни версией меньше нельзя.
Плюс `node_modules` не установлен, то есть **прямо сейчас проверить `npm test`
и `npm run build` невозможно**. Для проекта, который завтра стартует сезоном, это
странное состояние.

`api/Dockerfile:7`: `FROM node:22-alpine` — плавающий тег, при том что весь смысл
образа держится на том, что Node ≥ 22.18 умеет срезать типы. Версия, от которой всё
зависит, не закреплена.

## Напоследок

Раздражает в этом проекте не то, что он плохо сделан. Раздражает разрыв между
качеством размышления и качеством исполнения.

Комментарии здесь — лучшее, что я видел в подобных проектах: они объясняют, почему
масштаб целый, почему ключ — uuid, почему обход инвентарей лучше семи событий Bukkit,
почему снимок статистики честнее прироста. Каждое решение обосновано и проверено.

И при этом:

- в `crew.json` нет ни одного uuid, ради которого написан весь абзац про смену ников;
- `api` кладёт в разблокировки **ник**, вопреки собственному правилу;
